# RepoPilot 任务契约 v1

本契约定义首版任务输入、输出与成功判定，不定义执行器内部状态机。正式任务使用 JSON，按 `schemas/task.schema.json` 检查基本格式，再通过运行前检查。

## 1. 输入字段

八个字段全部必填，不接收未定义字段。

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | string | 1–64 个 ASCII 字符，以字母或数字开头，只含字母、数字、点、下划线、连字符；任务编号保持稳定，每次运行使用独立输出目录。 |
| `repoPath` | string | 可信本地 Git 仓库的绝对路径；不接受仓库 URL。存在性与绝对路径由运行前检查确认。 |
| `baseCommit` | string | 仓库内真实存在的完整 40 位小写十六进制提交号；分支名、HEAD、短提交号和占位符不作为正式输入。首版仅支持 SHA-1 仓库。 |
| `issue` | string | 问题描述，写明复现条件、实际行为、预期行为；不得包含密钥。 |
| `reproduceScript` | string | 仓库 `package.json` 中已有的 npm script 名称，例如 `test:reproduce`。只填写名称，不填写 shell 命令或额外参数。 |
| `regressionScript` | string | 仓库已有的 npm script 名称，例如 `test:regression`。其测试集合在基准版本全部通过。 |
| `expectedFailure` | string | 基准版本应失败的一个具体测试的完整名称；在复现结果中必须恰好匹配一个用例。执行器从结构化结果识别，不能只搜索任意日志；名称重复须先消除歧义。 |
| `allowedPaths` | string[] | 至少一个允许修改的具体源码文件，使用仓库相对路径和 `/` 分隔；不使用通配符，不能重复；测试、配置、依赖和任务文件不纳入允许范围。当前执行器限于 `src/` 下已提交的具体 JS/TS 常规源码文件。 |

`reproduceScript` 与 `regressionScript` 指向两个明确的测试集合：前者覆盖约定的失败测试，后者覆盖原本正常的用例。回归集合不包含故意失败的复现测试，避免要求基准版本同时失败和全部通过。

可通过 `task init [repoPath]` 向导生成上述 JSON。向导固定所选仓库当前的已提交 HEAD，列出该提交中的脚本与可授权源码，由用户选择两个不同脚本名、输入失败测试全名并明确选择文件。脚本名不同不保证测试集合互不重叠，仍需由基准检查核对。创建任务不执行脚本；保存后的基准预检查须另行确认，任务创建成功与缺陷复现、修复成功分别记录。

任务文件不提供模型、API Key 或任意环境变量；这些由宿主程序独立管理。首版不设计预算配置、插件配置或远程仓库下载字段。

第七步的定位在 `allowedPaths` 这个明确授权集合中选取相关子集，任务仍保存全部授权文件。`propose` 只向模型提供本次选中的完整源码，并拒绝编辑未选文件；`verify` 继续独立使用原始任务授权。定位不自动加入授权路径，规则与固定上下文预算见 `docs/LOCALIZATION.md`。

## 2. 运行前检查

JSON Schema 只检查字段、类型和基本格式，不证明仓库、提交、路径或测试真的存在。执行器实现后还必须检查：

1. 目标是可信本地仓库，`baseCommit` 可以解析且与实际工作副本版本一致。
2. 从该提交准备工作副本与依赖，不重置原仓库，也不纳入原仓库未提交修改。
3. 两个 npm scripts 均存在，执行目录为任务工作副本的仓库根目录；模型不能改写命令。
4. 允许修改的文件存在且属于源码；路径规范化及符号链接解析后不能越出工作副本。
5. 测试、脚本定义、配置和依赖文件的基准完整性记录在修改前建立。任务定义与验收程序由宿主管理，Agent 无权修改。
6. 测试运行能够提供用例文件路径、完整名称、结果与跳过状态；目标名称必须唯一匹配。基础设施错误不能冒充测试断言失败。

不满足这些条件时不得进入修复；报告真实原因，不生成伪造的成功结果。

## 3. 输出约定

每次运行使用独立输出目录，避免同一任务重复运行时覆盖证据：

```text
<本次运行目录>/
  report.json
  patch.diff       # 仅在实际生成代码修改时存在
  logs/            # 仅包含实际执行步骤的日志
```

`report.json` 至少包含：

| 字段 | 内容 |
|---|---|
| `taskId` | 输入任务编号。 |
| `baseCommit` | 实际使用的完整提交；若未能确认，则为 null，并说明原因。 |
| `status` | 下一节定义的四种终态之一。 |
| `reason` | 简洁结论或失败原因，不包含凭据。 |
| `changedPaths` | 最终补丁涉及的全部仓库相对路径；无修改时为空数组。 |
| `checks` | 实际执行的检查记录：修改前/后、脚本名称、实际执行命令、退出码、具体测试文件路径、完整名称与 passed/failed/skipped 结果、日志路径。 |
| `artifacts` | 实际生成的补丁及日志路径；不存在的补丁为 null，不指向虚构文件。 |

未执行的检查不伪造退出码或测试结果。若执行被中断、没有可靠退出码，应记录 null 和中断原因。报告、日志与补丁必须对应最终同一份代码；验收后再修改代码必须重新验收。

## 4. 最终状态

| `status` | 判定 |
|---|---|
| `resolved` | 满足下节全部成功条件。 |
| `unresolved` | 有效基准下已进行修复尝试，但候选补丁不合法，或补丁引起编译、导入、测试失败；保留证据。 |
| `not_reproduced` | 测试环境与复现脚本正常执行，但基准版本没有出现约定的目标测试失败。 |
| `error` | 输入、仓库、依赖或独立于补丁的执行/证据故障阻止可靠验收；超时、中断也归此类，并在 reason/checks 中区分。 |

基准检查时，脚本缺失、依赖失败、零测试执行、目标测试缺失、跳过或匹配多个用例，均不能当作已复现，记为 error；目标测试确实执行且通过，记为 not_reproduced。

若基准回归集合未全部通过，该任务不满足首版验收前提，记为 error，不启动修复。

基准有效后，能够确认由候选补丁引起的编译/导入失败、断言失败、用例缺失或跳过，记为 unresolved。独立环境故障、无法可靠采集证据或无法确认失败原因，记为 error；超时和中断统一记为 error。全部非 resolved 状态在后续评测中均不能计为修复成功。

## 5. 修复成功的全部条件

1. 修改前，指定目标测试实际执行并失败；不是环境错误或其他测试失败。
2. 修改前，约定回归集合实际执行并全部通过。
3. 最终补丁非空；所有源码修改都在 `allowedPaths` 中，没有越界、删除或新增未授权文件。范围检查也包含未跟踪文件，不能只看已跟踪文件的 diff；执行器的报告与日志保存在工作副本外。
4. 修改后，同一个目标测试实际执行并通过，复现集合全部通过；零测试、缺失或跳过均不算通过。
5. 修改后，原回归集合实际执行并全部通过，无新增失败、缺失或跳过。
6. 任务定义、验收测试、脚本定义、配置、依赖及验收程序保持原样；报告与日志证明以上检查针对最终补丁执行。

任意一项不满足，不能给出 resolved。模型声称修复、进程退出码为 0、只通过部分测试，均不足以单独证明成功。

## 6. 示例模板与阶段边界

`tasks/pagination-empty.template.json` 描述分页演示缺陷：空数组分页的 totalPages 应为 0。第三步已创建本地示例仓库，并在 `tasks/pagination-empty.json` 中保存其真实故障提交和绝对路径；基准复现与回归测试已实际执行。

模板继续使用明确的提交占位符，因此能解析为 JSON，但不能通过正式任务 Schema。运行时使用填入真实提交的正式任务文件；迁移到其他本机路径时需修改 repoPath。不得填造看似真实的提交号或已成功的结果报告。

第一步的完成标准是文档自洽、格式约束清楚、模板占位符可识别；不要求在此阶段实现 CLI、执行器、Agent、测试解析器或演示仓库。

第三步的 `baseline` 只验证修复前提，输出 `baseline.json`，使用独立的 `baselineStatus: ready | not_reproduced | error`；不冒用本契约的四种修复终态。当前测试协议固定为 node:test 事件生成的结构化 JSONL，具体支持范围见 `docs/BASELINE.md`。只有后续修复流程才生成正式任务报告并按本契约判断 resolved。

`verify` 接收人工或 `propose` 生成的候选补丁，重新建立基准并输出本契约规定的 `report.json` 和四种终态。通过完整性、测试和交付补丁回放后才可得到 resolved。每个 npm script 只允许一次 node:test 调用（可包含多文件），多进程覆盖证据须报 error。依赖准备完成后、测试执行前验证链接目标位于工作副本内，详细支持范围见 `docs/VERIFY.md`。

第八步的 `repair` 在单进程内最多生成 3 次候选，每轮审阅后调用上述独立验收器，符合条件的失败才反馈到下一轮。汇总 `repair.json` 使用 `kind: repair_run`，包含流程状态 `awaiting_review`；各轮正式验收报告仍遵循本契约四种终态。任务、所选原始源码和最终 JSON 用户消息的 32 KiB 限制保持固定，详见 `docs/REPAIR.md`。
