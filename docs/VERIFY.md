# 第四步：独立候选补丁验收

`verify` 接收任务文件和候选补丁，独立判断是否满足任务契约。补丁可以由人提供，或由 `propose` 生成；验收命令自身不调用模型。

## 运行正确示例

```powershell
cd D:\项目\RepoPilot
npm.cmd run dev -- verify tasks/pagination-empty.json patches/pagination-empty.fix.diff
```

预期 `status: "resolved"`，CLI 退出码为 0。修复仅在独立工作副本中应用，`D:\项目\RepoPilot-demo` 中的故障基准保持原样，以便重复验收。

示例候选把空数组分页的 `totalPages` 从强制至少为 1 改为实际页数。验收结果应包含：修改前目标断言失败、六项回归通过；修改后目标和原回归全部通过。

另有两份可运行反例：

| 候选文件 | 预期结果 |
|---|---|
| `patches/pagination-empty.fix.diff` | `resolved`：合法修复，测试通过，导出补丁回放一致。 |
| `patches/pagination-empty.wrong.diff` | `unresolved`：仍未修复目标行为。 |
| `patches/pagination-empty.test-tamper.diff` | `unresolved` / `PATCH_SCOPE_INVALID`：修改验收测试，拒绝执行修复后测试。 |

将命令最后一个参数换为相应文件即可验证。反例退出码为 1 是预期的拒绝结论。任务和候选补丁不得包含凭据。

## 验收顺序

1. **重新建立基准。** 每次都复用第三步管线从真实提交创建新的 detached worktree，执行依赖准备和修改前测试，不复用历史报告的结论。
2. **建立完整性记录。** 保存工作副本全部实际文件的类型、权限和 SHA-256，包含依赖、ignored 和 untracked 文件；记录任务、宿主代码、Schema、项目依赖定义的哈希。快照不保存文件原文。
3. **应用候选并检查范围。** 在私有工作副本执行 `git apply --check` 后再应用。只允许 `allowedPaths` 中原有常规源码文件的非空内容修改；新增、删除、测试/配置/依赖变化、链接或权限变化均拒绝。
4. **重跑两个测试集合。** 使用相同脚本、宿主 reporter 与环境白名单。目标必须完整名称唯一、文件身份不变；每个原有测试的文件、完整名称和出现次数必须保留。全部修复后用例须通过，不接受零测试、缺失、跳过或 TODO。
5. **确认同一代码版本。** 每次测试结束都重新采集快照，并核对 HEAD、宿主验收程序和任务没有变化。运行中改代码、测试或依赖时中止，不输出过期补丁。
6. **验证交付补丁。** 从指定基准提交导出统一格式的非空 `patch.diff`。再建立第二个干净工作副本，应用这份导出补丁，检查范围并比较所有允许源码文件的内容、类型和权限，确认能够重建实际测试的版本。

```mermaid
flowchart LR
    B[故障基准成立] --> A[应用候选]
    A --> S[范围与完整性]
    S --> T[目标及回归测试]
    T --> F[最终快照稳定]
    F --> R[导出补丁并回放]
    R --> O[正式报告]
```

## 正式报告

复用的基准管线为每次验收创建独立 `.repopilot/runs/baseline-*/` 目录：

```text
baseline.json        # 本次修改前检查的历史记录
report.json          # 本次补丁验收的正式结论
candidate-input.diff # 实际应用的输入副本，读取成功后才存在
patch.diff           # 可稳定导出且回放一致时才存在
logs/                # 命令、用例、快照哈希及 reporter 写入标记
worktree/            # 实际测试的候选工作副本
patch-replay/        # 导出补丁的干净回放副本，创建后保留
```

`baseline.json` 记录修改前事实；其中的工作副本随后会承载候选。完整验收以 `report.json` 为准。

| `status` | 含义 | CLI 退出码 |
|---|---|---|
| `resolved` | 有效基准、非空合法修改、目标及回归通过、最终快照稳定、交付补丁回放一致。 | 0 |
| `unresolved` | 基准有效，但候选非法、未修复、导致编译/导入或测试失败、遗漏用例，或检查期间改变工作副本。 | 1 |
| `not_reproduced` | 基准目标实际执行并通过，不能证明原缺陷；不应用候选。 | 1 |
| `error` | 输入、环境、超时、中断、宿主变化、证据缺失或矛盾等故障阻止可靠结论。 | 2 |

`checks` 只记录实际执行的检查，保留脚本、命令、真实退出码、具体文件和完整测试名称。修复后检查的 `snapshot` 标记发起检查时的候选版本。启动失败或中断不伪造退出码；不记录原始 stdout、stderr、异常或断言实际值。

`integrity.candidate` 与 `integrity.final` 必须一致，且 `stable` 和 `replayVerified` 均为 true，才可能得到 `resolved`。这些标志本身不表示测试通过：稳定的错误补丁仍可导出，最终结论必须查看 `status`。

空补丁、不能应用、越界、无法取得一致快照或无法回放时，不保留指向虚构或过期 `patch.diff` 的引用。实际执行过的证据与工作副本仍保留供审查。

## 首版边界

- 延续可信本地 Windows / Node / npm / package-lock / node:test 环境。原任务八个字段不变，候选补丁是独立的 CLI 参数。
- 每个 npm script 只允许一次 `node --test` 调用；该调用可包含多个文件。宿主 reporter 使用独占 `.writer` 标记，重复写入会留下 `.multiple` 并被拒绝，避免后一次进程覆盖前一次失败。当前不聚合多个独立测试进程的报告。
- 链接不会被递归跟随；启动测试前拒绝越出工作副本、断开或无法解析的链接，防止工作区外依赖绕过完整性检查。内部链接的目标文件仍须处于被完整扫描的工作副本中。
- 会扫描已安装依赖的文件。依赖很多时完整性检查需要更多时间；测试若写缓存或生成文件，也会被视为版本变化而拒绝。当前演示无需第三方依赖。
- Git 内部数据库不作为文件树递归扫描；工作副本 `.git` 指针、HEAD、实际交付源码和补丁回放另行校验。
- worktree 用于隔离文件修改，不是恶意代码安全沙箱。当前不运行不可信仓库，不声称覆盖任意恶意运行时行为。

第五步的 `propose` 可以生成候选补丁。审阅 `artifacts.patch` 后，将其路径传给 `verify` 获取独立结论。
