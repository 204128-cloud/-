# RepoPilot 简历与面试材料

## 简历项目

**RepoPilot｜可独立验收的代码缺陷定位与修复 Agent**

**技术栈**　TypeScript、Node.js、Pi SDK、Qwen、TypeBox、Git worktree、node:test

- 基于 Pi SDK 和 Qwen，在 AI 协作下实现面向可信 Node.js 单仓库的修复 CLI。按问题与失败测试名排序授权源码，将修复请求的 JSON 上下文限制在 32 KiB，校验结构化编辑的路径和原文匹配。
- 实现模型外的独立补丁验收。人工审阅后，从固定提交新建 Git worktree，先复现缺陷，再重跑目标测试与原有回归，并通过快照和干净工作副本回放确认交付补丁重建了受测版本。符合条件的测试失败会将上一轮 diff 和测试摘要反馈给模型，每次修复运行最多尝试 3 次模型调用。
- 实现 Pi 风格终端交互，支持流式回复、取消执行、多行草稿、本地图片附件、文字会话保存恢复，以及不经过模型的运行历史、配置诊断和报告查看。
- 构建独立的同预算对照：无反馈与带反馈策略各最多 3 次，独立采样、审阅和验收。三项构造开发案例经真实 Qwen 运行，两策略各首轮通过 3/3 项，合计 6 次请求尝试；该批未触发失败反馈。核心代码通过 343 项自动化测试，类型检查与构建通过。

## 60 秒面试介绍

我用 Pi SDK 和 Qwen，在 AI 协作下做了一个单仓库代码修复 Agent。Pi 提供模型接入和工具接口，我主要做了任务契约、受限编辑和独立验收，也接入了可聊天、附图和查看报告的终端界面。模型只读选中的授权源码，提交结构化编辑；每轮人工审阅后，验收器在新 Git worktree 复现缺陷，重跑原测试，再回放补丁核对交付版本。失败时最多尝试三轮。旧 Unicode 实测曾拦住一个回归失败的候选，反馈后第二轮通过。新增三项构造案例又做了同预算独立对照，共六次真实请求，两策略都首轮通过，所以这批还不能说明反馈是否更有效。

## 面试追问

### 你做了哪些工程决策？

Pi SDK 提供模型适配和工具调用。我的主要工作是定义任务与成功条件，设计白名单、上下文和重试预算，并实现和验证补丁验收及评测流程。开发中使用了 AI 协作。项目在可信本地仓库运行，Git worktree 用来隔离文件修改。

### 怎样判断交付的补丁就是实际测过的版本？

验收器先确认原提交的目标测试失败、原有回归通过，再应用审阅过的候选。它校验修改范围与原测试身份，要求修复后的目标和回归全部通过。测试前后核对快照，再在第二个干净工作副本回放导出补丁，确认回放结果与受测源码一致。[独立验收规则](VERIFY.md)

### 首轮失败后，模型具体收到了什么？

后续请求保留首轮选中的源码和固定基准，加入上一候选的完整 diff 以及目标测试和回归测试的结构化摘要，整个 JSON 用户消息仍限 32 KiB。Unicode 案例中，首轮移除了连字符转义，导致字符类回归失败。第二轮改用 Unicode 转义，目标和 6 项回归全部通过。[反馈规则与实测](REPAIR.md)

### 这次评测能说明什么？

2026-11-13 的 `extended-v1` 是两条策略各最多三次的独立对照，三项均首轮通过，六份验收各自重跑目标和八项回归，补丁回放也通过。无反馈执行共 73.8 秒，反馈配置共 77.5 秒，均扣除了审阅回调等待，包含模型和整个验收流程。小样本、单次运行和未触发反馈使它无法证明反馈收益、总体修复率或速度优劣。[同预算实测与可迁移结果](EQUAL_BUDGET.md#本机实测)

2026-11-10 的 `smoke-v1` 则是共享首候选的两案例演示：首轮通过 1/2 项（2 次调用），反馈流程通过 2/2 项（合计 3 次调用），预算不同。这批展示了实际失败反馈的过程；两批实验分开陈述，不合并成总体成绩。[旧评测记录](BENCHMARK.md#本机实测)

### 如何现场展示，避免依赖模型当场发挥？

使用保存的真实 Qwen 补丁，离线重建冻结案例并独立验收。展示修复前失败、修复后目标与回归通过、完整性与补丁回放报告；再打开三案例实测快照说明调用数及结论范围。现场演示不新增 API 请求。[演示步骤](DEMO.md)
