# RepoPilot 面试问答手册：120 问

适用岗位：AI 应用 / Agent 开发。内容依据当前项目源码、343 项自动化测试记录和已保存的真实评测。问题无法穷尽，本手册覆盖项目高频问题及主要追问；答案用于理解和练习，应按自己实际参与和掌握的程度表达。

## 使用方法

先练 1、3、11、21、51、61、101、103、111、120 题，再按模块深入。每题先用 30–60 秒概括，再打开对应源码解释一处实现。回答统一采用“解决什么问题 → 怎样实现 → 如何验证 → 有什么限制”。

当前事实：单用户、本地、可信 JS/TS 仓库、Pi SDK + Qwen、人工确认、独立验收；没有生产客户、多租户、向量数据库、多智能体协作或总体成功率提升的实证。未来方案必须明确说“尚未实现”。

## 一、项目介绍与贡献

### 1. 用一分钟介绍一下这个项目。

我在 AI 协作下，基于 Pi SDK 和 Qwen 做了 RepoPilot，一个本地代码修复 Agent。模型在授权源码范围内生成候选，人工审阅后，宿主在新 Git worktree 中重新复现缺陷、重跑目标与回归测试，再回放补丁核对交付版本。符合条件的失败可以反馈给模型，最多三轮。当前有 343 项自动化测试通过，也有小规模真实 Qwen 记录，结论限定于已测案例。

### 2. 它解决什么具体问题？

模型能够输出看起来合理的代码，但输出是否适用于同一版本、是否破坏原行为、最终补丁是否对应实际受测代码，都需要额外验证。RepoPilot 把输入约束、审阅、实际测试和补丁回放组织成可重复流程，并输出证据。

### 3. Pi 已经有 Agent 能力，你增加了什么？

Pi 提供模型适配、工具接口和终端组件。本项目增加任务契约、固定故障提交、源码授权与上下文预算、结构化编辑校验、独立验收和回放、失败反馈及评测编排。贡献应通过这些模块和测试说明，保留 Pi 来源与 AI 协作说明。

### 4. 这是从零开发的吗？

这是基于开源 SDK 的应用开发，开发过程中也使用 AI 协作。可以说明哪些约束与流程由本项目实现、如何验证；不应把 Pi、Qwen 或上游公开案例说成自己的原创成果。

### 5. 为什么选择代码修复场景？

这个场景有明确的输入版本和可执行测试，便于把模型输出转化为可核对结果，也适合研究工具调用、状态控制、反馈和评测。代价是当前只覆盖预先准备好的小范围任务。

### 6. 用户实际怎样使用？

先为可信仓库固定提交，指定复现脚本、回归脚本、失败测试名及允许修改的源码。可以用 CLI 分步运行，也可以绑定任务进入终端聊天。生成候选后审阅，确认才验收，最后查看报告和导出补丁。

### 7. 谁是目标用户？

当前适合开发者在可信本地 JS/TS 仓库上处理范围明确、已有复现测试的缺陷。项目没有验证大型企业、多用户托管或任意语言仓库，因此不把这些场景当作现有能力。

### 8. 哪个工程设计最值得讲？

独立验收与补丁回放。候选生成和最终成功判定分开：验收器从原任务重建基准，检查原测试和完整性，再把导出补丁应用到第二个干净副本，核对交付源码是否与受测版本一致。

### 9. 项目最主要的限制是什么？

当前依赖可信本地仓库、SHA-1 Git、package-lock 和 node:test，源码位置及修改范围也受限。测试通过只证明满足现有验收用例；无法证明全部语义正确，也没有恶意代码沙箱或生产规模验证。

### 10. 使用 AI 开发时，怎样证明你理解项目？

现场沿一条任务说明输入、模型请求、候选校验、审阅和验收各发生在哪里，解释关键测试为什么失败或通过。对 AI 参与程度据实说明；不把“能复述文档”当作已经掌握实现。

依据：[架构](ARCHITECTURE.md)、[简历材料](RESUME.md)、[来源声明](../NOTICE.md)。

## 二、架构与技术选型

### 11. 整体架构怎样分层？

入口层是 CLI/TUI，聊天层处理模型对话和任务工具；任务管线负责基准、定位、提议、审阅和修复编排；验收层负责测试证据、快照与回放；存储层保留运行报告和文字会话。模型调用集中在 Pi 适配层。

### 12. 一次修复的完整数据流是什么？

任务 JSON → 固定提交的基准工作副本 → 目标失败与回归通过 → 授权源码筛选 → 模型提交结构化编辑 → 宿主导出候选 → 人工确认 → 独立验收 → 交付补丁及报告。可重试的失败会形成下一轮输入。

### 13. 为什么用 TypeScript 和 Node.js？

Pi SDK 与当前终端组件可直接在这一生态使用，类型系统便于约束报告、工具和状态，Node 提供进程、文件和 node:test 能力。代价是首版的依赖、测试脚本和执行支持范围偏向 Node 仓库。

### 14. 为什么用 Pi SDK，而不是自己写模型客户端？

复用模型适配、流式事件和工具调用接口，可以把主要工作放在修复约束与验收上。同时用适配层集中处理认证、超时和响应校验，减少业务代码直接依赖供应商协议的地方。

### 15. 为什么没有使用 LangChain 或 LangGraph？

当前流程固定、规模较小，现有 SDK 加显式编排已经能表达状态和停止条件。没有做过充分的框架性能比较，因此不宣称当前方案优于其他框架；选择依据是当前需求与实现复杂度。

### 16. 为什么采用 Git worktree？

它能从同一个固定提交建立独立文件副本，不重置用户原仓库，也便于重复验收和补丁回放。它隔离文件修改，但共享 Git 对象库，并不限制测试进程的系统权限。

### 17. 为什么同时提供 CLI 和 TUI？

CLI 便于分步调试、脚本调用和读取结构化报告；TUI 便于聊天、滚动查看 diff、管理附件和完成交互确认。两种入口复用核心任务流程，避免各自定义一套成功标准。

### 18. 为什么没有数据库？

当前是单用户本地工具，独立运行目录和有界 JSON 文件足以支持报告追踪。数据库会引入迁移和部署成本；如果以后需要多用户检索、并发写入和事务，再设计存储模型。

### 19. 为什么不一次做成 Web 服务？

本地工具能够直接操作可信仓库，缩小首版范围。Web 服务还需要用户隔离、权限、远程执行沙箱和任务调度，这些目前没有实现，不能把现有 CLI 直接暴露成公网执行接口。

### 20. 如何验证分层没有只停留在文档？

可以从 `cli.ts` 找到入口分派，从 `chat.ts` 找到两个任务工具，再沿 `repair.ts` 进入提议和验收模块。源码模块有独立职责，测试也分别覆盖输入、工具、状态和实际 Git/测试流程。

依据：[模块表](ARCHITECTURE.md#模块分工)、[CLI](../src/cli.ts)、[聊天层](../src/chat.ts)。

## 三、Agent、模型与工具调用

### 21. 为什么可以称为 Agent？

绑定任务后，模型能根据用户请求提出定位或修复工具调用，宿主确认并执行，再把工具结果交给模型总结；修复管线还能根据失败证据有限迭代。它是受限、有人参与的 Agent，当前没有开放式自主规划和任意工具执行。

### 22. Function Calling 与普通文本建议有什么区别？

工具调用给出工具名和结构化参数，宿主可以校验并决定是否执行。普通文本中的“我已经运行测试”不会触发执行，也不能成为成功证据；最终状态来自实际任务管线。

### 23. 项目有哪些模型工具？

聊天绑定任务时提供 `locate_task` 和 `repair_task`；候选生成阶段通过 `submit_edits` 收集结构化替换。连接冒烟检查还有固定只读的 `read_probe`，它只用于验证 SDK 工具链路。

### 24. 一条聊天消息最多调用模型几次？

普通回复通常一次。定位工具通常包含工具决策和结果总结两次；修复工具还会进入最多三次候选生成，正常完整路径最多五次模型请求尝试。这里要区分“每条问题最多一次任务工具”和“工具内部最多三次修复尝试”。

### 25. 模型能自己执行任意 shell 吗？

当前没有给模型开放任意 shell 工具。测试命令由已固定任务中的 npm script 名称选择，编辑也须经过宿主校验。但仓库内的脚本本身会执行代码，因此仍要求仓库可信。

### 26. 模型提交未知工具、多个工具或坏参数怎么办？

宿主检查工具数量、名称、参数解析状态和契约，不符合就停止该操作。没有把工具参数交给 `eval`；模型文本中描述某种操作也不会绕过验证。

### 27. 工具结果总结时再次请求工具怎么办？

总结请求设置不允许工具选择，返回后仍检查回复是否携带工具调用。无效总结不会导致第二个任务工具执行，界面可回退到已经取得的实际工具结果。

### 28. 如何设计提示词？

系统指令定义受限职责，并要求把源码、任务、图片和反馈视作数据；用户 JSON 提供问题、测试摘要和完整选中源码。提示词用于引导行为，真正的修改范围和成功判定仍由宿主代码执行。

### 29. 如何处理模型幻觉？

检查结构化编辑能否唯一匹配原文、路径是否允许、实际测试是否通过及补丁是否可回放。模型声称成功不会自动变成 `resolved`；这些措施降低错误交付风险，但不证明模型不会产生幻觉。

### 30. 当前用了 RAG、多智能体或微调吗？

没有。当前是词法源码筛选、受限工具调用和有限反馈流程，没有向量检索、多个模型角色协作或模型训练。以后可以作为独立实验引入，并用相同验收器比较。

依据：[模型适配](../src/pi.ts)、[聊天工具与调用控制](../src/chat.ts)、[编辑 Schema](../src/repair-edits.ts)。

## 四、任务契约与源码定位

### 31. 任务 JSON 包含什么？

八个字段：`id`、`repoPath`、`baseCommit`、`issue`、`reproduceScript`、`regressionScript`、`expectedFailure`、`allowedPaths`。分别固定任务身份、仓库与版本、问题、测试和修改授权，不在任务里保存密钥或任意环境变量。

### 32. 为什么固定提交，不能直接使用 HEAD？

分支和 HEAD 会移动，同一任务可能在不同代码上运行。正式任务使用完整真实提交号，管线核对工作副本 HEAD，使原问题、测试、源码和补丁有明确的版本参照。

### 33. 为什么要分复现与回归脚本？

复现集合确认目标缺陷存在，回归集合确认原本正常的行为。回归集合应排除故意失败的目标用例；两个脚本名字不同，不代表它们的测试集合就一定分离，仍要检查实际证据。

### 34. 任务向导会替用户写测试吗？

不会。它读取已提交仓库中的脚本和源码，让用户选择、填写失败测试全名与授权文件，再确认保存。创建任务成功与基准就绪分开，选择预检后才执行依赖准备和测试。

### 35. JSON Schema 校验通过是否代表任务可执行？

只代表字段和基本格式符合约束。真实提交、文件、脚本和测试是否存在，以及目标是否真的失败，必须通过运行前检查和基准执行确认。

### 36. `allowedPaths` 有什么作用？

它是用户明确授权的具体源码集合，当前限制在 `src/` 下的常规 JS/TS 文件。模型不能扩展这个集合，也不能把测试、配置或依赖文件加入修改范围。

### 37. 当前怎样定位源码？

从问题描述和失败测试名提取词，对授权文件的路径和内容做词法匹配。路径命中权重为五，内容命中权重为一；按分数和稳定路径顺序排序。这是可解释的启发式，不是语义检索或完整调用图分析。

### 38. 中文和标识符怎样处理？

英文单词转小写，并拆分常见驼峰标识符；连续中文生成相邻双字片段，过滤一些常见无区分度的英文词。这种方法简单，但同义词、间接依赖和跨文件语义可能匹配不到。

### 39. 没命中文件时怎么办？

授权集合只有一个文件时允许单文件回退；多个文件都没有命中时明确失败，让用户补充符号、文件名或问题信息，不随意挑一个文件给模型。

### 40. 为什么限制完整文件和上下文字节数？

完整文件减少片段丢失局部语义的问题，同时用最多三个文件、1 MiB 本地扫描和 32 KiB JSON 用户消息控制规模。32 KiB 包含 JSON 转义和测试摘要，不等于模型全部上下文窗口；超限会拒绝或跳过候选文件，而不是静默截断源码。

依据：[任务契约](TASK_CONTRACT.md)、[任务校验](../src/task.ts)、[词法定位](../src/localization.ts)。

## 五、候选编辑与补丁

### 41. 为什么让模型提交结构化编辑？

宿主可以明确检查路径、原片段和替换片段，再统一导出 Git diff。减少直接解析混合解释文本、代码围栏或模型生成补丁头部的歧义，但仍然需要验证编辑语义和测试结果。

### 42. 一条编辑有哪些字段？

`path`、`before`、`after`。路径必须属于本轮选中源码，`before` 必须在原文件中精确且唯一匹配；宿主据此替换，模型不直接决定写入任意文件。

### 43. 原片段出现两次为什么拒绝？

否则无法知道模型要改哪一处，按第一处替换可能误改。当前要求模型给出更完整、能唯一定位的片段，使用明确失败代替猜测。

### 44. 模型能一次改多个文件吗？

可以，但只能改当前上下文实际选中的文件，每个文件最多一条替换；定位最多选三个文件。Schema 的编辑数组上限和实际可编辑文件数不是一回事，运行时还会检查选中文件和重复编辑。

### 45. 编辑大小如何限制？

每个替换片段限制 16 KiB，并检查实际 UTF-8 字节、空字符和 Unicode 合法性；累计修改后文件内容限制为 64 KiB。不能只靠 JSON Schema 的字符串长度代替字节检查。

### 46. Windows 换行如何处理？

匹配时统一规范 CRLF/LF，拒绝混乱或无法可靠处理的换行，再按原文件风格恢复。需要避免模型输出的换行差异导致无法匹配或产生整个文件的无意义改动。

### 47. 删除内容和没有变化的编辑如何处理？

`after` 可以是空字符串，因此允许删除一个片段；但 `before` 不能为空，前后相同会被拒绝。最终仍需非空合法补丁，不能用空操作声称修复成功。

### 48. 模型能新建、删除或重命名文件吗？

当前修复只允许已授权常规源码文件的内容修改，不提供新增、删除和重命名授权。这样缩小了修改空间，也限制了需要新模块或跨结构重构的任务。

### 49. 候选哈希解决什么问题？

把审阅时看到的具体补丁字节与后续验收绑定。TUI 预览核对 SHA-256，修复流程也再次检查；确认后补丁被改动不能沿用旧审阅。哈希用于内容一致性，不证明代码质量。

### 50. 如何防止预览内容欺骗终端？

有界读取完整补丁，核对 UTF-8、控制字符、凭据模式和候选哈希，再由宿主添加颜色。无法安全完整展示就不进入确认。当前预览上限是 256 KiB，不能只展示一小段却让用户批准整份未知补丁。

依据：[结构化编辑](../src/repair-edits.ts)、[候选生成](../src/proposal.ts)、[审阅读取](../src/patch-review.ts)。

## 六、独立验收与完整性

### 51. 怎么判定修复成功？

原提交必须实际复现约定缺陷，原回归通过；候选合法、非空，修改后目标与原有回归均通过；任务、宿主与文件快照保持可靠；导出补丁在干净副本回放后能重建受测源码。最终结论由验收器给出。

### 52. 为什么生成完补丁还要重新建立基准？

避免直接继承候选生成副本中的状态或过期结论。验收独立从原任务和固定提交开始，重新取得修复前测试证据，再应用审阅过的候选。

### 53. 怎样证明目标测试真的运行了？

宿主 node:test reporter 输出结构化用例证据，包括文件、完整名称、状态和是否断言失败，并保留完成标记。目标必须按完整名称唯一匹配，不能用任意日志里出现的文字代替测试事实。

### 54. 为什么检查断言失败？

依赖缺失、导入异常或语法错误不等于目标行为被复现。基准阶段要求可靠的断言故障和正常回归，防止把环境坏了误当成有效修复起点。

### 55. 模型修改测试让它通过怎么办？

测试不在允许修改集合中，补丁范围和完整性检查会拒绝相关改动。修复后还检查原用例的文件、完整名称和出现次数，防止目标消失、重名、跳过或集合被缩减。

### 56. 只有退出码 0 为什么不够？

脚本可能没执行测试、后一个进程覆盖前一个失败，或测试数量发生变化。项目把退出码与结构化证据一起核对，要求集合有效、状态一致且原测试身份保留。

### 57. 为什么要求每个脚本一次 node:test 调用？

当前证据协议没有实现多个独立测试进程的聚合。reporter 使用独占写入标记，重复写入留下异常标记，避免后一进程覆盖前一进程的失败；多进程测试框架需要另做可靠聚合适配。

### 58. 文件快照包括什么？

记录文件类型、内容哈希、权限和链接等信息，并扫描实际工作副本中的依赖及未跟踪文件。测试若改写源码、生成额外文件或改变依赖，会影响一致性判断；这也是当前不适合任意复杂仓库的原因。

### 59. 补丁回放具体验证什么？

把导出的补丁应用到第二个干净工作副本，检查授权源码内容、类型和权限是否与受测候选一致。它证明交付补丁重建了被测试的版本，不额外证明业务逻辑在所有输入上正确。

### 60. 有 patch.diff 就表示成功吗？

不表示。稳定、可回放但仍有测试失败的候选也可能保留补丁作为失败证据。应看正式 `report.json` 的状态、测试、完整性和回放记录，不能只看文件存在或模型回答。

依据：[验收规则](VERIFY.md)、[验收器](../src/verifier.ts)、[证据判定](../src/evidence.ts)、[完整性](../src/integrity.ts)。

## 七、失败反馈与有限重试

### 61. 首轮失败后模型收到什么？

保留原问题、原始授权源码与基准摘要，追加上一候选的完整 diff，以及修改后目标与回归测试的结构化摘要。不是把无限增长的终端日志全部发给模型，也不泄露未筛选的原始断言值。

### 62. 下一轮修改上一轮结果还是原始源码？

提交编辑仍针对同一份原始源码。上一候选作为反馈数据供参考，这样每份候选都能独立应用到固定基准，避免依赖一串难以追踪的叠加编辑。

### 63. 所有错误都会重试吗？

不会。只有符合规则、证据可靠的测试失败才继续。认证、基础设施、完整性、无效编辑和上下文异常等会停止；盲目重试这些错误既增加成本，也可能掩盖问题。

### 64. 为什么最多三轮？

这是当前实现的明确调用预算，控制运行时长和尝试次数，避免无界循环。它不是实验证明的最优值；改变预算应作为新的实验设计，重新比较成功率、调用和时间。

### 65. 重复补丁如何处理？

记录已经生成的候选哈希，再次生成相同补丁时停止，避免对相同内容重复审阅和验收。产生重复候选的那次请求已经发生，仍需计入调用尝试。

### 66. 反馈超过上下文限制怎么办？

完整 JSON 用户消息仍限制在 32 KiB，包含转义后的 diff、证据和源码。当前超限会停止，不偷偷删掉失败证据或截断代码；摘要压缩可以是未来方案，但不能说已经实现。

### 67. 用户拒绝候选会怎样？

保留候选并返回等待审阅状态，停止后续验收和重试。没有把拒绝视为测试失败，也没有自动应用到原仓库；重复启动是新的运行，当前不支持从原评测中途恢复。

### 68. 四种正式验收终态怎么区分？

`resolved` 是满足验收条件；`unresolved` 是有效基准下候选未满足条件；`not_reproduced` 是原目标实际通过，未复现缺陷；`error` 是输入、环境或证据异常导致无法可靠判断。修复编排额外有 `awaiting_review`，不能与验收成功混淆。

### 69. 基准就绪与候选已生成是否代表修好了？

`ready` 只表示缺陷复现且回归正常；`located` 表示选中了上下文；`proposed` 表示产生候选。它们是不同阶段的事实，最终成功需要独立验收，不能用较早阶段覆盖较晚失败。

### 70. 自动重试和人工审阅是否矛盾？

程序自动决定是否还有重试资格并组织下一次请求，但每个候选仍需人工审阅后才能验收。这是有限自动化与明确人工控制结合的取舍，没有实现无人值守修复。

依据：[重试实现](../src/repair.ts)、[反馈与真实案例](REPAIR.md)、[任务终态](TASK_CONTRACT.md)。

## 八、多模态与会话

### 71. 本地图片是怎样发送给模型的？

宿主读取本地文件，检查普通文件类型、大小和图片签名，编码为 SDK 的图片内容。模型请求携带真实图片字节；单独发送一个本地路径字符串，模型不会因此获得文件系统访问能力。

### 72. 支持什么图片和多大文件？

当前一条消息一张 PNG、JPEG 或 WebP，最大 5 MiB，类型根据字节签名识别。格式签名检查不等于完整图像解码或内容安全审查，也不代表模型一定能准确理解图片。

### 73. 为什么曾出现模型说无法访问本地图片？

旧输入入口只把“路径加问题”当文字发送，未读取图片。后来增加消息开头本地图片路径的识别，同时保留 `/image`；回归检查问题和图片参数，并用真实 SDK 对本机接口核对完整字节，防止只测到字符串解析。

### 74. 附图失败或替换失败会怎样？

新图片读取失败会清除旧待发送附件，避免误发旧图。已加载图片在模型请求失败或取消后保留，便于明确重试；图片成功发送、清空对话或成功恢复会话后，待发附件按规则清空。

### 75. 每次请求会发送全部历史吗？

不会。模型请求保留最近八轮完整问答及其中最近一张图片；界面历史和手动保存的文字可以更多。模型上下文窗口、界面记录和持久化会话是不同层次。

### 76. 为什么只保留最近一张图片？

控制请求体大小和图片上下文开销，同时让最近附图更容易成为当前问题的视觉依据。代价是无法依靠当前实现做多张历史图片的完整对比，需要明确重新附图或扩展设计。

### 77. 保存会话包含哪些数据？

手动保存已完成的文字问答、图片省略标记、报告引用和任务指纹；不保存图片原始数据、凭据或可自动重放的工具参数。退出不自动保存，失败和中断的半轮也不作为完整问答保存。

### 78. 会话文件有什么限制？

最多 200 轮、总文件不超过 1 MiB，并检查字段、UTF-8、控制字符和疑似凭据。超限拒绝而不静默截断；恢复的显示历史可以多于八轮，后续模型请求仍只取最近窗口。

### 79. 为什么恢复会话要核对任务指纹？

任务编号相同不保证授权文件、提交或问题没有变化。保存任务文件的字节指纹，并在恢复时核对，防止把旧上下文恢复到另一份任务授权中。

### 80. 恢复会话会执行旧工具或重新验收吗？

不会。恢复文字和历史报告引用，不重放工具，不恢复图片字节，也不把历史成功当成本次重新验证。用户需要新的操作时，重新提出请求并经过当前确认。

依据：[图片读取与解析](../src/chat-image.ts)、[会话存储](../src/session-store.ts)、[聊天历史](../src/chat.ts)。

## 九、终端交互与并发控制

### 81. TUI 的基本交互是什么？

Pi 终端组件绘制滚动对话区、底部多行编辑器和状态栏。Enter 发送、Shift+Enter 换行；当前 Ctrl+J 无动作，多行粘贴仍保留换行。Ctrl+C 复制所选文字，Ctrl+Q 或 `/exit` 退出，Esc 中断当前操作或退出消息选择。

### 82. 流式回复是怎样实现的？

聊天层通过 `streamSimple` 消费文本增量，界面更新同一个回复组件。工具参数和思考事件不直接展示；完整响应还要经过停止原因与工具契约检查，才进入正式历史。

### 83. 用户在生成过程中继续提问会怎样？

当前 TUI 会展示“排队发送 / 引导当前回答”选择。排队在当前回复成功结束后顺序发送；引导会取消旧请求，等它结束后结合原问题和补充要求重新请求。其他本地命令和审阅期间的输入按相应草稿规则处理。

### 84. 怎样避免同时发送两个聊天请求？

界面维护忙碌状态、当前请求和活动 Promise，队列在当前操作结束后排空下一项。引导也等待取消的旧请求收尾；已有用例检查请求不重叠，而不是只检查界面显示顺序。

### 85. 引导回答会丢失原问题或图片吗？

当前保存被引导轮次的问题和附件，组合原问题与补充要求，必要时保留该图片。它是一次新的模型请求；如果原请求已经完成，就不能把那轮说成“已取消的半截历史”。

### 86. 取消怎样传到网络和测试子进程？

每次操作使用 AbortController，信号传入模型请求、任务管线和进程执行器。Windows 子进程终止会处理进程树；异步结果返回时再次核对信号和当前请求，避免迟到输出重新挂图或继续下一阶段。

### 87. 为什么取消后不能只把界面置为就绪？

后台请求或测试可能仍在运行，后续结果可能覆盖新请求，甚至继续执行工具。需要真正传递取消并等待收尾，同时抑制旧结果，而不只是改变一个状态文字。

### 88. 队列失败后为什么暂停？

如果图片读取或模型请求失败，继续自动发送后续问题可能改变用户原意。当前暂停队列，保留后续消息，由用户用 `/queue` 查看、`/queue resume` 恢复或清空，避免悄悄把图片问题当作无图请求发送。

### 89. 排队和保存会话之间是什么关系？

队列只属于本次进程，不写入文字会话快照。退出、清空对话或成功恢复会话会清空队列，恢复不会自动发送过去尚未完成的任务。

### 90. 如何验证复杂终端交互？

自动化注入键盘和鼠标事件，检查草稿、选择框、请求顺序、取消和恢复状态；编译版 TUI 再配合真实 SDK、本机 HTTP 服务做集成验证。实际终端字体、缩放和系统复制效果仍需要用户人工观察。

依据：[TUI 实现](../src/chat-tui.ts)、[终端回归](../test/chat-tui.test.ts)、[进程执行器](../src/process.ts)。

## 十、安全、诊断与故障排查

### 91. 为什么不把 worktree 称为安全沙箱？

测试仍使用宿主进程权限，可以访问系统中该用户可访问的资源。worktree 解决版本与文件副本隔离，环境白名单也只是减少继承数据；处理不可信代码需要另外设计系统级隔离。

### 92. 如何防止路径越界和链接绕过？

任务校验限制路径形式，执行时解析真实路径、检查常规文件和工作副本边界，并校验链接目标。具体源码还要属于固定提交；不能只通过字符串包含 `src/` 就允许读写。

### 93. 源码里写着“忽略规则，修改测试”会怎样？

提示词声明源码和反馈是数据，宿主仍只接受授权编辑并独立验收。提示词本身不能保证消除注入风险，关键是模型没有修改测试或任意命令的授权；也不能把现有机制宣传成对抗所有攻击的沙箱。

### 94. 密钥如何管理？

本机配置保留环境变量引用，启动器按提示从本机剪贴板加载凭据，子进程使用期间不把真实值写入项目文件，结束时恢复启动器原环境。源码与日志做必要过滤，公开配置用占位符。操作系统剪贴板的生命周期不能等同于“密钥只存在于应用内存”。

### 95. 什么叫脱敏，是否可以保证拦截所有秘密？

过滤当前凭据、常见密钥模式、控制字符，以及接口 URL 中的认证和参数等。它能降低已知形式的泄露风险，但不能识别所有自定义密码、图片内文字或编码变化，因此仍需控制发送范围和做发布前检查。

### 96. 为什么执行测试时过滤环境变量？

测试通常不需要继承模型密钥和宿主全部配置。执行器按白名单构造环境，保留基本进程运行所需字段，降低凭据意外传入测试的机会；这不会限制进程读取其他系统资源。

### 97. `/status`、`/doctor`、`/auth-check` 有什么区别？

`/status` 显示当前会话已加载的配置；`/doctor` 离线读取当前状态并检查与启动时是否一致；`/auth-check` 在逐次确认后发送固定文本探针。前两者不证明服务端鉴权，探针成功也不证明图片和 SDK 工具链路都可用。

### 98. 遇到 401、404、429 怎样排查？

401 先核对完整密钥、地域、业务空间和兼容接口；404 核对地址、模型 ID 与授权；429 检查频率与配额。保留脱敏状态和已知错误码，逐项改变配置，不能仅凭一次状态就认定某个唯一原因。

### 99. 鉴权通过，但聊天或工具失败怎么办？

固定非流式 HTTP 探针与 SDK 流式对话、图片及工具调用是不同路径。应分别检查同一接口和凭据、代理、响应格式、模型能力声明及实际 SDK 请求；用本机模拟接口区分客户端差异和真实服务问题。

### 100. 发布到 GitHub 前检查了什么？

按 Git 实际候选范围扫描凭据样式、私人接口、个人路径和文档链接，忽略本机配置、运行任务和日志，提供公开模板并保留来源声明。再用待发布文件独立安装、测试和演示；MIT 是本项目许可，第三方原有声明继续保留。

依据：[凭据与网络适配](../src/pi.ts)、[状态投影](../src/chat-status.ts)、[发布记录](PUBLISHING.md)、[许可证](../LICENSE)。

## 十一、测试、评测与结果解释

### 101. 343 项测试能说明什么？

说明当前代码在记录的环境中通过了这些自动化检查，包含输入、异常、交互及真实 Git/测试管线。它们不等于 343 个真实线上缺陷，也不是模型修复成功率、测试覆盖率或生产稳定性的百分比。

### 102. 单元、集成和真实模型测试如何区分？

纯函数或文件契约测试检查局部规则；集成测试实际运行 Git、测试进程、SDK 和本机 HTTP 服务；真实模型测试才访问百炼。模拟服务验证协议与控制逻辑，不能替代模型质量或当前鉴权。

### 103. 真实百炼到底测了多少，结果怎样？

就已归档的两批修复评测分开说：旧两案例共享首候选，首轮通过 1/2 项，反馈流程通过 2/2 项，整次实际三次调用。新增三构造案例采用独立同预算对照，两策略各首轮通过 3/3 项，合计六次请求尝试。这不包含调通期间的鉴权、冒烟和聊天请求，也不是全部 API 账单；两批数据不能合并为总体成功率。

### 104. 能说反馈让成功率从 50% 提升到 100% 吗？

可以如实描述旧两案例观察到的数量，但不能据此声称总体提升或因果效果：两条流程预算不同、共享首候选，案例又用于开发。新增公平对照全部首轮成功，也没有实际触发失败反馈。

### 105. `bench` 和 `bench-equal` 有什么区别？

`bench` 比较共享同一首候选的单轮与最多三轮反馈流程，不能把共享调用重复相加。`bench-equal` 独立生成无反馈与反馈两臂，各最多三次，并按任务交替执行顺序；两种设计和计数分别记录。

### 106. 同预算为什么实际调用数还可能不同？

相同的是最多三次的上限。成功、重复候选、用户拒绝或错误可以提前停止，不能强迫已成功的一臂继续消耗调用。比较时应同时报告预算、实际尝试、停止状态和固定任务分母。

### 107. 新三案例上限为什么是十八次，实际为什么只有六次？

三任务乘两策略乘每策略三次上限，得到十八次。该次每组首轮就通过，因此实际是三加三，共六次；不能把上限写成实际使用量，也不能把无反馈首轮视为复用了反馈候选。

### 108. 调用次数和耗时怎样统计？

调用计数记录进入请求回调的尝试，包括失败尝试，不是账单或严格的 HTTP 用量。耗时分别记录墙钟时间、审阅等待和扣除等待的执行时间；执行时间还包含 Git、依赖、测试和回放，不是纯模型延迟。

### 109. 有哪些真实失败案例值得讲？

旧 Unicode 案例的一个修复轮次让目标测试通过，但字符类回归失败，被独立验收拦下；收到反馈后第二轮通过。还应区分早期单次提议的另一份失败补丁，不能把不同运行拼成同一条时间线。

### 110. 怎样证明反馈确实有用？

需要更多未用于调试的独立任务、相同模型和预算、明确的失败状态与重复运行，比较反馈和无反馈重采样，并报告不确定性和实际成本。当前三构造案例及单次运行不足，不能补写没有做过的统计结论。

依据：[旧实验](BENCHMARK.md)、[同预算实验](EQUAL_BUDGET.md)、[公开结果快照](../benchmarks/results/extended-v1-qwen-2026-11-13.json)、[测试验收](FINAL_ACCEPTANCE.md)。

## 十二、质疑、改进与现场演示

### 111. “这是不是给 Pi 换皮？”怎么回答？

先承认复用了 Pi 的模型和终端能力，再展示独立任务契约、编辑白名单、测试证据、回放及评测模块。用一个被回归拦截的补丁说明实际增量；不靠 Logo 和聊天界面证明技术贡献。

### 112. “这些代码都是 AI 写的吧？”怎么回答？

据实说明 AI 参与了哪些开发步骤，以及自己能负责说明的需求取舍、审查、验证和修改。现场解释关键代码和失败测试，比模糊声称所有实现都独立手写更可信；不编造个人经历或团队分工。

### 113. “模型只修了几个简单案例，有什么价值？”怎么回答？

小案例适合验证管线的约束、证据和停止条件，但模型能力结论确实有限。项目价值可落在可重复执行与验收的工程实现上；更复杂真实缺陷和外部任务集是后续评测工作。

### 114. “测试通过不一定正确，你的验收有什么意义？”

同意测试不是完整规格。验收把结论限定为固定版本和原有用例约束，防止缺失测试、篡改或错交版本等问题；更强的业务保证需要更好的测试、人工审查或额外验证方法。

### 115. “为什么不用 Docker 就说安全？”

当前只声明可信仓库和文件副本隔离，不声称具备不可信代码执行安全。未来若托管外部仓库，需要进程权限、资源、文件系统和网络隔离；不能只加一个容器命令就宣称解决所有安全问题。

### 116. “如何降低延迟和费用？”

现有措施包括有限上下文、调用预算、提前停止和去重。以后可分析基准安装、快照和模型分别占用的时间，研究可信缓存；缓存必须绑定版本与依赖，不能跳过独立验收或把历史结果直接当本次成功。

### 117. “如何扩展到大仓库或更多测试框架？”

先定义新的输入、证据和完整性契约，再适配源码选择及测试 reporter。大仓库可研究符号和依赖分析，其他框架要处理用例身份、跳过、失败类型和多进程聚合；这些目前没有完成，不能只修改脚本名就保证支持。

### 118. “如果改成多人 Web 服务，需要补什么？”

需要身份与仓库授权、用户隔离、任务持久化、执行环境、队列调度、资源与调用预算，以及审阅和报告 API。当前前端队列只管理本机 TUI 的消息，不能等同于服务端任务调度系统。

### 119. “有没有生产用户、收益或大规模性能数据？”

没有可据以声称的生产客户、收入、线上 SLA 或并发压测数据。可以展示公开仓库、本机测试和有边界的真实模型记录；未来目标与已经发生的结果分开表达。

### 120. 现场怎样用三分钟证明项目能工作？

先解释端口字符串缺陷和固定任务，再展示保存的真实 Qwen 补丁；离线运行独立验收，打开报告说明修复前目标失败、八项回归通过，修复后全部通过和回放一致。最后说明 Pi 来源、个人增量、AI 协作及小样本边界。现场不依赖服务配额，也不把离线重放算作新模型成绩。

## 附录：常用术语速查

| 术语 | 怎样解释 | 与本项目的关系 |
|---|---|---|
| Token | 模型分词后的单位，与字符、字节不一一对应。 | 项目的 32 KiB 是 JSON 用户消息字节限制，不是 32K tokens；模型输入还包含系统指令和工具定义。 |
| 上下文窗口 | 一次模型请求可处理的信息范围。 | 最近八轮是应用的历史策略，不等于模型窗口大小，也不保证这八轮任意长度都能被服务接受。 |
| Temperature / top-p | 控制采样分布的参数，会影响输出变化。 | 当前没有建立这些参数的系统调优实验；相同提示也不能保证得到相同补丁，不应编造最优参数。 |
| Embedding | 把文本等数据映射到向量，用于相似度比较等任务。 | 当前没有计算源码向量，不能把词法匹配说成向量检索。 |
| RAG | 检索相关资料，再把检索结果提供给生成模型。 | 当前会筛选授权源码，但没有实现向量数据库或成熟知识库 RAG 管线。 |
| Tool Calling | 模型输出工具名与结构化参数，程序决定是否执行。 | 模型不直接获得系统权限，宿主要检查工具名、参数、确认状态与结果。 |
| 结构化输出 | 按预定结构输出内容，减少解析歧义。 | 有结构不等于参数合法，更不等于业务正确；仍需 Schema、原文匹配与实际测试。 |
| SSE | 服务端通过 HTTP 持续传输事件的一种方式。 | 当前兼容接口的流式事件由 SDK 接收，聊天层处理文本增量；不是前后端 WebSocket 应用。 |
| 超时、重试、取消 | 超时限制等待，重试创建新尝试，取消终止当前操作。 | 三者分开处理；SDK 自动重试与应用根据测试反馈重新生成候选，也不是一回事。 |
| 幂等性 | 重复操作是否保持相同的可观察结果。 | 相同补丁验收可以产生新报告，实际模型调用也可能不同，因此整条修复流程不声称严格幂等；重复候选只是在单次运行内去重。 |
| TOCTOU | 检查时与使用时状态不一致的竞态问题。 | 审阅前后核对补丁哈希、执行前后核对任务和快照，有助于发现变化；不能据此宣称恶意宿主下没有竞态。 |
| 内容哈希 | 把内容映射为固定长度摘要，用于核对一致性。 | SHA-256 用于候选和快照；SHA-1 是当前支持的 Git 提交格式。两者用途不同，哈希本身不证明逻辑正确。 |
| 异步与并行 | 异步描述等待方式，并行描述同时执行。 | 网络和子进程使用异步等待，但 TUI 主动把聊天请求顺序执行；不能把 async/await 当成高并发能力的证据。 |
| 类型检查与运行时校验 | 类型检查帮助开发期发现错误，运行时校验检查实际外部数据。 | TypeScript 类型不能保证模型 JSON 合法，所以工具和任务还需要 TypeBox / Schema 与语义检查。 |
| 可观测性 | 能从状态、事件和证据理解系统发生了什么。 | 当前有阶段进度、结构化报告、计数和哈希；没有部署分布式追踪、监控平台或线上告警系统。 |
| 可复现性 | 用明确输入和环境再次执行并核对结果。 | 固定案例和验收可重复运行；真实模型输出具有变化，重复实验需要记录新调用与新结果，不能沿用旧成绩。 |

若被问到具体模型训练、注意力推导、向量索引算法或生产调度，应说明这与当前项目实现的关系，再按自己掌握的知识回答。不要把概念解释包装成本项目已经实现的功能。
